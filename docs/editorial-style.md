# Public writing style

Use plain American English for the dashboard, README, FAQ, and other public explanations. This follows the user's requested style and the plain-language and clear-prose guidance in `~/projects/personal/writing-style`.

The approach is inspired by Simplified English and analytical writing. It is a project writing policy, not a claim of formal compliance with a controlled-language standard.

- State the main point first. Name the action and the government that took it.
- Use familiar, precise words and active verbs.
- Write complete sentences with normal word order. Keep one main point in each paragraph.
- Define a necessary legal or technical term when it first appears. Use the same term consistently after that.
- Attribute reports and keep the dates that matter. Distinguish proposals, adopted actions, effective dates, reported votes, and certified results.
- Explain each limitation where readers need it. Avoid repeating the same qualification in every sentence.
- Keep build logs, model request counts, internal handoff labels, hashes, and review procedures in technical records. The main page should explain the data and help people use it.
- Avoid metaphors, slogans, rhetorical questions, forced transitions, and promotional language.
- Use ordinary punctuation. Break up long lists of clauses joined by semicolons or dashes.
- Preserve uncertainty and source wording when it affects the facts. Do not strengthen a claim to make a sentence shorter.

Count checks must follow the published wording. Use named HTML elements for generated values so a count update does not require restoring an old sentence. Review the rendered page after editing a template.

The shared writing tools can flag long sentences and repeated phrases. Treat those findings as prompts for review, not as a measure of factual accuracy or writing quality.
